# Тестове завдання — API погодження документа

> Джерело: `test_task (1).pdf`. Текст перенесено без змін, лише відформатовано в Markdown.

Відведіть на виконання до 60 хвилин разом із тестами та README. Після цього надішліть поточний результат і коротко зазначте, що не встигли. Додаткові функції не потрібні.

## 01. Обсяг і стек

Реалізуйте невеликий ASP.NET Core Web API на .NET 8 або новіше з in-memory сховищем. Достатньо одного API-проєкту та проєкту тестів. Використовуйте безкоштовні для цього завдання залежності.

База даних, UI, справжня автентифікація, Docker, брокер повідомлень та зовнішні сервіси не потрібні. `actorId` у запиті лише імітує поточного користувача.

## 02. Три операції API

- `POST /api/approval-tasks`: прийняти номер документа, назву та `assigneeId`. Сервер задає ID, статус `Assigned`, однакові дати створення й зміни в UTC та порожню історію. Відповідь: `201` і створена задача.
- `POST /api/approval-tasks/{id}/actions`: прийняти `actorId`, дію `Start`, `Approve` або `Reject`, необов'язковий коментар. Відповідь після успіху: `200` й оновлена задача.
- `GET /api/approval-tasks/{id}`: повернути `200`, поля задачі та історію успішних дій.

## 03. Бізнес-правила та цілісність

- Лише призначений виконавець може виконувати дію. Переходи: `Assigned -> InProgress` через `Start`; `InProgress -> Approved / Rejected` через відповідну дію.
- Для `Reject` потрібен непорожній коментар. Після `Approved` або `Rejected` будь-яку наступну дію відхиляйте.
- Успішна дія одночасно змінює статус, дату зміни й додає історію: дія, виконавець, коментар, час UTC. Помилка не змінює жодних даних. GET має повертати узгоджений стан.
- Якщо два паралельні запити намагаються погодити або відхилити ту саму задачу в `InProgress`, лише один має завершитися успішно. Другий отримує `409`; у історії залишається одне фінальне рішення. Просте блокування в межах одного процесу допустиме.
- Обов'язкові текстові поля не можуть бути порожніми або містити лише пробіли. Відсутня чи невідома дія — `400`; відсутня задача — `404`; інший виконавець — `403`; недозволений перехід — `409`. Помилки повертайте зі зрозумілим повідомленням.

## 04. Перевірка

Покрийте unit-тестами бізнес-правила: повний успішний шлях до погодження або відхилення; недозволений перехід, зокрема після фінального стану; чужий виконавець; відхилення без коментаря. Для помилок перевірте незмінність стану й історії. Кількість тестових методів не фіксується; параметризовані тести доречні.

Додайте перевірку двох конкурентних фінальних дій на рівні сервісу. Окремий HTTP-тестовий проєкт і навантажувальний стенд не потрібні.

## 05. Що надіслати

Посилання на репозиторій або архів. У короткому `README.md`: команди запуску API й тестів, приклади створення та дії, спосіб захисту від конкурентних змін, відомі обмеження.

AI можна використовувати. У `AI_USAGE.md` вкажіть інструмент, суттєві промпти дослівно, що застосували чи змінили та як перевірили результат. Якщо AI не використовували, достатньо одного речення.

Оцінюємо коректність бізнес-логіки, зрозумілість коду, тести й обґрунтованість рішень. Велика кількість шарів або бібліотек не дає додаткових балів.
